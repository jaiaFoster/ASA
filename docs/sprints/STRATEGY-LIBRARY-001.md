# STRATEGY-LIBRARY-001 — Autonomous Sprint Prompt

**Purpose:** prove ASA can add useful strategy breadth cheaply and safely through the existing shared data/runtime/product architecture.

Read the program prompt first.

## Strategy selection authority

This sprint is authorized to implement a first wave without returning to the Founder for routine selection. Choose strategies using these priorities:
1. source methodology is sufficiently explicit to implement faithfully;
2. it matches the Founder’s options-first direction;
3. data requirements overlap strongly with capabilities ASA already acquires;
4. exact structure/entry semantics can be represented truthfully;
5. it adds a meaningfully different opportunity type rather than a cosmetic variant;
6. no paid provider purchase is required merely to start.

Target:
- **2–4 additional option strategies**
- **1–2 additional stock strategies** if source semantics and current data support them.

If repository/source evidence does not uniquely define a strategy’s material semantics, skip that candidate and choose another. Escalate to Founder only when the ambiguous strategy is uniquely necessary to the product.

## Intake pipeline

Each strategy must pass:

```
source/reference
 -> formal strategy specification
 -> data/capability declaration
 -> reusable analytics mapping
 -> pure strategy judgment
 -> exact structure/position semantics
 -> generic runtime registration
 -> scheduled/current operation
 -> API projection
 -> user-facing card
 -> typed failure diagnostics
 -> observation
```

## Work packages

### SL-01 — Strategy intake template
Create a repository template/checklist that captures:
- source and version/date;
- entry gates;
- exit/lifecycle if applicable;
- structure;
- expiration rules;
- strike/delta rules;
- liquidity;
- exclusions;
- calculations and reusable analytics;
- capabilities;
- UNKNOWN behavior;
- expected user presentation.

Resolve the existing manifest/contract doctrine mismatch before multiplying it: choose one accepted architectural path or obtain Architect decision and document the reconciliation. Do not proliferate a known ambiguity.

### SL-02 — Options wave
Implement selected options strategies one at a time through the generic architecture. Reuse shared requests and derived facts. Each strategy must reach exact trade proposal or typed terminal reason.

### SL-03 — Stock wave
Implement selected stock strategies using the same intake discipline and stock product path.

### SL-04 — Strategy health/library UI
Expose what strategies exist, their version/status, required capabilities, current evaluation coverage, and actionable-result counts. Do not rank strategy quality yet from inadequate samples.

### SL-05 — Operational observation
Verify the expanded library under real scheduled/current operation and record capability pressure/provider call behavior. If strategy breadth reveals provider capacity stress, optimize reuse/batching first; only then quantify a procurement blocker.

## Acceptance

Adding a strategy is demonstrably a bounded composition task, not a new subsystem. Every added production strategy uses one market-data authority, generic runtime, typed UNKNOWN semantics, and the corresponding user-facing proposal path.

## Transition

OUTCOME-INTELLIGENCE-001 may begin as soon as stable opportunity identities/tracking exist; it does not need to wait for every SL strategy observation window.
